# サイト名・URL設計案

## 最終決定

**ドメイン分離を採用**

| ドメイン | 用途 | サイト名 | 時期 |
|----------|------|----------|------|
| `marcopolo-portal.jp` | エンドユーザー向け（イベント参加、アンケート） | - | 現在 |
| `admin.marcopolo-portal.jp` | 社員向け管理画面（顧客・イベント・管理者管理） | **Marcopolo Admin** | 現在 |
| `kansa.marcopolo-portal.jp` | 監査役向け求人サイト | 未定 | 将来 |

### URL構造

```
marcopolo-portal.jp/
└── /events/
    ├── /[id]/rsvp    → イベント参加回答
    └── /[id]/survey  → アンケート回答

admin.marcopolo-portal.jp/
├── /login            → ログイン
├── /customers        → 顧客管理
├── /events           → イベント管理
└── /admins           → 管理者管理
```

### 実装方針

- **プログラムは1つ**（単一のNext.jsアプリ）
- **Vercelで複数ドメインを設定**
- **Middlewareでドメインに応じたルーティング制御**
- **Cookie共有**: `domain: '.marcopolo-portal.jp'` で設定
- 将来的にアプリ分離が必要になった場合も対応可能

### 採用理由

- エンドユーザーが「admin」ドメインでイベント参加するのは違和感がある
- ドメイン分離によりURLがわかりやすい
- 開発上の追加コストは許容範囲内（Middleware設定、Cookie設定程度）

## 検討過程

### 管理系サイトのURL候補

#### 案1: admin.marcopolo-portal.jp

```
admin.marcopolo-portal.jp/
├── /login            → ログイン
├── /customers        → 顧客管理
├── /events           → イベント管理
├── /admins           → 管理者管理
└── /events/[id]/rsvp → 参加回答（エンドユーザー）
```

**メリット**: 管理画面であることが明確
**デメリット**: エンドユーザーがadminドメインでイベント参加するのがやや違和感

---

#### 案2: marcopolo-portal.jp（ルートドメイン）

```
marcopolo-portal.jp/
├── /admin/           → 管理画面
│   ├── /customers
│   ├── /events
│   └── /admins
└── /events/          → エンドユーザー向け
    ├── /[id]/rsvp
    └── /[id]/survey
```

**メリット**:
- ルートドメインはポータル的な位置づけで自然
- エンドユーザーは`/events/`でアクセス

**デメリット**: 将来拡張時に整理が必要になる可能性

---

#### 案3: community.marcopolo-portal.jp

```
community.marcopolo-portal.jp/
├── /admin/           → 管理画面
└── /events/          → エンドユーザー向け
```

**メリット**: コミュニティ運営という位置づけが明確
**デメリット**: kansaと並列のサブドメインになる

## 開発上の比較: 同一ドメイン vs サブドメイン分離

### 同一ドメイン（admin.marcopolo-portal.jp に統合）

```
admin.marcopolo-portal.jp/
├── /admin/           → 社員用管理画面
└── /events/[id]/rsvp → エンドユーザー向け
```

| 観点 | 評価 |
|------|------|
| **デプロイ** | ✅ 1つのアプリをデプロイするだけ |
| **認証・セッション** | ✅ Cookie共有が自然。同一オリジン |
| **CORS設定** | ✅ 不要 |
| **環境変数・設定** | ✅ 1セット |
| **インフラコスト** | ✅ 1つのVercel/サーバーで済む |
| **開発の複雑さ** | ✅ シンプル |
| **UX観点** | ⚠️ エンドユーザーがadminドメインを見る違和感（軽微） |

### サブドメイン分離（admin + ルートドメイン）

```
admin.marcopolo-portal.jp/ → 社員用管理画面
marcopolo-portal.jp/       → エンドユーザー向け
```

| 観点 | 評価 |
|------|------|
| **デプロイ** | ⚠️ 同一アプリでも2つのドメイン設定が必要 |
| **認証・セッション** | ⚠️ サブドメイン間でCookie共有するには設定が必要（domain=.marcopolo-portal.jp） |
| **CORS設定** | ⚠️ API呼び出しでCORS設定が必要になる可能性 |
| **環境変数・設定** | ⚠️ ドメインごとの設定が増える |
| **インフラコスト** | ✅ 同一アプリなら変わらない |
| **開発の複雑さ** | ⚠️ やや複雑（ルーティング、ドメイン判定など） |
| **UX観点** | ✅ URLがわかりやすい |

---

## 結論

開発上は同一ドメイン（admin.marcopolo-portal.jp）が圧倒的にシンプルだが、エンドユーザーがURLを見る機会（イベント参加依頼メール、アンケート依頼メール）を考慮し、**ドメイン分離を採用**した。
