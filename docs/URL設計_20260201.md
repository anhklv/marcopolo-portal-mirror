# サイト名・URL設計案

## 最終決定（2026/02/06 更新）

**1ドメイン・パスベースのルーティングを採用**

| パス | 用途 | サイト名 |
|------|------|----------|
| `marcopolo-portal.jp/admin/...` | 社員向け管理画面（顧客・イベント・管理者管理） | **Marcopolo Admin** |
| `marcopolo-portal.jp/events/...` | エンドユーザー向け（イベント参加回答、アンケート） | - |

### URL構造

```
marcopolo-portal.jp/
├── /admin/
│   ├── /login                → ログイン
│   ├── /customers            → 顧客管理
│   ├── /events               → イベント管理
│   ├── /admins               → 管理者管理
│   ├── /settings/password    → パスワード変更
│   ├── /sitemap              → 画面一覧（DEBUG_ADMIN_PANEL=true のみ）
│   └── /styleguide           → スタイルガイド（DEBUG_ADMIN_PANEL=true のみ）
├── /events/
│   ├── /[id]/rsvp            → イベント参加回答
│   └── /[id]/survey/[token]  → アンケート回答（トークン認証）
└── /docs/                    → ドキュメント閲覧（本番では非公開）
```

※ `/docs` は開発・クライアント確認用。本番環境では Middleware でブロックまたはビルドから除外する。

### 実装方針

- **単一のNext.jsアプリ、1ドメイン**
- パスプレフィックスで管理画面（`/admin/`）とエンドユーザー向け（`/events/`）を分離
- 本番アプリのルーティングでサブドメイン不要のため、Cookie設定・CORS設定・ドメイン判定ロジックは一切不要（ステージング環境のサブドメインは別途運用）
- Vercelでのデプロイも1ドメイン設定のみ

### 採用理由

- エンドユーザーが見るURLに「admin」が含まれない（`/events/[id]/rsvp`）
- サブドメイン分離と同じUXメリットを、追加の複雑さなく実現できる
- Cookie共有・CORS・Middleware でのドメイン判定が不要で圧倒的にシンプル
- 現在のコード構造（`/admin/...` と `/events/...`）がそのまま本番で動く

## 検討過程

### 比較: サブドメイン分離 vs 1ドメイン

#### サブドメイン分離（旧案）

```
admin.marcopolo-portal.jp/ → 社員用管理画面
marcopolo-portal.jp/       → エンドユーザー向け
```

| 観点 | 評価 |
|------|------|
| **デプロイ** | 同一アプリでも2つのドメイン設定が必要 |
| **認証・セッション** | サブドメイン間でCookie共有するには設定が必要 |
| **CORS設定** | API呼び出しでCORS設定が必要になる可能性 |
| **環境変数・設定** | ドメインごとの設定が増える |
| **Middleware** | ドメイン判定ロジックが必要 |
| **UX観点** | URLがわかりやすい |

#### 1ドメイン・パスベース（採用案）

```
marcopolo-portal.jp/
├── /admin/  → 社員用管理画面
└── /events/ → エンドユーザー向け
```

| 観点 | 評価 |
|------|------|
| **デプロイ** | 1つのドメイン設定のみ |
| **認証・セッション** | 同一オリジンのため自然に動く |
| **CORS設定** | 不要 |
| **環境変数・設定** | 1セット |
| **Middleware** | ドメイン判定不要 |
| **UX観点** | エンドユーザーのURLに admin が含まれない |

### 結論

サブドメイン分離のUXメリット（エンドユーザーにadminを見せない）は、パスベースの分離でも同様に達成できる。開発・運用コストを考慮し、**1ドメイン・パスベースのルーティングを採用**した。
