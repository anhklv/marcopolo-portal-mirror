# Next.js 設計案（2026/02/21）

> 04-Next.jsベストプラクティス設計案_20260128.md の後継。
> フェーズ1（顧客管理・イベント管理）の実装完了時点の実態を反映。

## 基本方針

- Next.js App Router の Server Components / Server Actions を最大限活用する
- `_archive/mockup/` のUIをベースに、Shadcn UI コンポーネントで再構築する
- 層を増やしすぎない。**Actions → Repository の2層**で十分
- デザインの統一は粒度の小さいUIコンポーネント（`PageHeader`, `Stack`, `SectionHeading` 等）で担保する

## 各層の設計

### 1. Server Components（デフォルト）

すべてのページは Server Component。データ取得・権限チェックを行い、Client Component にシリアライズ済みデータを渡す。

```typescript
// app/admin/(authenticated)/customers/page.tsx
import { findAll } from "@/lib/repositories/customer.repository";
import { serializeCustomerForList } from "@/lib/serializers/customer";
import { CustomerList } from "./_components/customer-list";

export default async function CustomersPage() {
  const { isSuper, scopedCommunityIds } = await getAuthenticatedAdmin();
  const customers = await findAll(scopedCommunityIds, isSuper);

  return (
    <CustomerList
      initialCustomers={customers.map(serializeCustomerForList)}
      isSuper={isSuper}
      scopedCommunityIds={scopedCommunityIds}
    />
  );
}
```

### 2. Server Actions（データ更新）

`lib/actions/` に配置。Zod バリデーション → 権限チェック → Repository 呼び出し → `revalidatePath` + `redirect`。

```typescript
// lib/actions/customer.actions.ts
"use server";

import { customerFormSchema } from "@/lib/validations/customer";
import * as customerRepo from "@/lib/repositories/customer.repository";

export async function createCustomerAction(formData: unknown): Promise<ActionResult | void> {
  const session = await requireAuth();

  // Zod でバリデーション
  const parsed = customerFormSchema.safeParse(formData);
  if (!parsed.success) {
    return { fieldErrors: ... };
  }

  await customerRepo.create(parsed.data);

  revalidatePath("/admin/customers");
  redirect("/admin/customers");
}
```

### 3. Repository 層（データアクセス）

関数エクスポート。Prisma を直接使用。

```typescript
// lib/repositories/customer.repository.ts
import { prisma } from "@/lib/prisma";

export async function findAll(
  scopedCommunityIds: number[],
  isSuper: boolean,
  options?: { includeFormerMembers?: boolean }
) {
  return prisma.customer.findMany({
    where: { ... },
    include: { customerCommunities: { include: { community: true } } },
  });
}
```

### 4. Serializer 層（Date → string 変換）

Prisma の `Date` オブジェクトはそのまま Client Component に渡せないため、`lib/serializers/` で文字列に変換する。

```typescript
// lib/serializers/customer.ts
export function serializeCustomerForList(c: CustomerWithCommunities): SerializedCustomer {
  return {
    ...c,
    registeredAt: c.registeredAt.toISOString(),
    customerCommunities: c.customerCommunities.map((cc) => ({
      ...cc,
      joinedAt: cc.joinedAt?.toISOString() ?? null,
    })),
  };
}
```

### 5. Helper 層（純粋関数）

テスト可能なロジックを `lib/helpers/` に切り出す。UI層やServer Actions層から使用。

```typescript
// lib/helpers/customer-filter.ts
export function filterCustomers<T extends FilterableCustomer>(
  customers: T[],
  filters: CustomerListFilters
): T[] {
  return customers.filter((customer) => { ... });
}
```

### 6. Client Components

`_components/` ディレクトリに配置。`"use client"` を付与。

**フォームの構成:**
- `[機能名]-form.tsx` — 見た目（JSX）のみ
- `use-[機能名]-form.ts` — 状態管理・バリデーション・送信処理をカスタムフックに分離
- フォーム項目が多い場合はサブコンポーネント（`audit-community-fields.tsx` 等）に分割

**一覧の構成:**
- `[機能名]-list.tsx` — フィルタUI・テーブル表示・ページネーション
- フィルタロジックは `lib/helpers/` に切り出し

### 7. 定数（`lib/constants/`）

DB のコード値やラベルは `lib/constants/` に一元管理する。ハードコードしない。

```typescript
// lib/constants/community.ts
export const COMMUNITY_CODE = {
  VENTURE_AUDITOR: "venture_auditor",
  NAIKAN_MEETUP: "naikan_meetup",
  AI_CLUB: "ai_club",
  OTHER: "other",
} as const;
```

## データフロー

```
[読み取り]
  Server Component（page.tsx）
    → Repository（Prismaでデータ取得）
    → Serializer（Date → string 変換）
    → Client Component（_components/ に Props で渡す）

[書き込み]
  Client Component（useState 制御フォーム）
    → Server Action（Zod バリデーション + 権限チェック）
    → Repository（データ更新）
    → revalidatePath + redirect

[フィルタリング]
  Server Component（全件取得）
    → Client Component（useMemo でクライアント側フィルタ）
    → usePagination でページネーション
```

## UIコンポーネントの使い分け

旧設計では `FormPage`, `ListPage`, `DetailPage` という大きなレイアウトコンポーネントを計画していたが、実装では粒度の小さいコンポーネントの組み合わせを採用した。柔軟性が高く、各ページの要件に適応しやすいため。

| コンポーネント | 用途 |
|---|---|
| `PageHeader` | ページタイトル・説明・戻るリンク |
| `SectionHeading` | セクション区切りの見出し |
| `Stack` | セクション内の要素を一定の余白で配置 |
| `FormField` | ラベル＋入力＋エラーメッセージの3点セット |
| `DataItem` | ラベル＋値の2点セット（詳細画面用） |
| `ActionButton` | フォーム送信ボタン（中央寄せ・幅広） |
| `PaginationControls` | ページネーションUI |

### ボタンラベルの統一

| 操作 | ラベル |
|---|---|
| 新規作成（一覧ページ） | 「新規登録」 |
| フォーム送信（新規） | 「登録」 |
| フォーム送信（編集） | 「更新」 |
| 削除 | 「削除」 |
| 一覧に戻る | 戻る矢印アイコン（`PageHeader` の `backHref`） |

## Service 層について

現時点では導入しない。以下の状況が発生した場合に追加を検討する:

- 複数の Repository をまたぐトランザクション処理が必要になった
- Server Actions のロジックが肥大化してきた（目安: 1ファイル100行超）
- 同じビジネスロジックを複数の Actions から呼び出す必要が出てきた

追加する場合の配置:

```
lib/
├── services/
│   └── customer.service.ts    # Actions → Service → Repository
├── actions/
└── repositories/
```

## Rails/Laravel 経験者向けの対応表

| Rails/Laravel | 本設計 |
|---|---|
| Controller#index | Server Component（page.tsx） |
| Controller#show | Server Component（[id]/page.tsx） |
| Controller#new / #create | Client Component + Server Action |
| Controller#edit / #update | Client Component + Server Action |
| Controller#destroy | Server Action |
| Model (validation) | Zod スキーマ（lib/validations/） |
| Model (data access) | Repository（lib/repositories/） |
| Serializer / Presenter | Serializer（lib/serializers/） |
| Helper | Helper（lib/helpers/） |
| Service Object | 当面不要。必要時に lib/services/ に追加 |
| View template | Server/Client Component |
| `redirect_to` | `redirect()` + `revalidatePath()` |
| `before_action` | `requireAuth()` / `canAccessCustomer()` |
