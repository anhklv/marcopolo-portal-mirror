# 実装ガイドライン

本プロジェクト（マルコポーロ・ポータル）の実装規約をまとめたドキュメントです。
新しい画面や機能を作成する際は、本ガイドラインに従ってください。

---

## 1. 基本方針（技術スタック）

- **フレームワーク**: Next.js (App Router)
- **UIライブラリ**: Shadcn UI (Tailwind CSS)
- **通信**: Server Actions（API Routesは使用しない）
- **バリデーション**: Zod（`lib/validations/` に定義）
- **状態管理**: React Hook Form等は使用せず、標準の `useState`（Controlled Components）を採用

---

## 2. コーディング規約

### A. 定数の一元管理

DBのコードやマスタ値をコード上で参照する場合は、文字列リテラルを直接書かず `lib/constants/` の定数を使用すること。

**悪い例:**
```ts
// コミュニティコードの直書き
if (cc.community.code === "venture_auditor") { ... }
const audit = communities.find((c) => c.code === "venture_auditor");

// 日本語名での判定
if (eventTypeName === "ベンチャー監査役の会") return "audit";
```

**良い例:**
```ts
import { COMMUNITY_CODE } from "@/lib/constants/community";

if (cc.community.code === COMMUNITY_CODE.VENTURE_AUDITOR) { ... }
const audit = communities.find((c) => c.code === COMMUNITY_CODE.VENTURE_AUDITOR);
```

**定数ファイルの配置規則:**

| 対象 | ファイル |
|---|---|
| コミュニティコード・名前・バッジ | `lib/constants/community.ts` |
| 顧客関連（会員区分、会員種別等） | `lib/constants/customer.ts` |
| イベント関連（ステータス等） | `lib/constants/event.ts` |
| 管理者関連（ロール等） | `lib/constants/admin.ts` |

新しいドメイン固有の定数が必要な場合は、`lib/constants/[ドメイン名].ts` に追加すること。

### B. 型安全性

- `any` は使用禁止。Zodから推論された型（`z.infer<typeof schema>`）またはPrismaの生成型を使用すること。
- 定数マップは `satisfies` で網羅性チェックを行うこと。キーの追加漏れをコンパイル時に検出できる。

### C. UIコンポーネント

- `components/ui/` 以下のShadcn UIコンポーネントを使用すること。
- アイコンは `lucide-react` を使用すること。

## 3. フォーム実装ガイドライン

`app/admin/(authenticated)/customers/`（顧客管理画面）の実装パターンを規範とする。

### A. ファイル構成と役割分担

フォーム機能は以下のファイルセットで構成すること。

1. **`page.tsx` (Server Component)**
   - データの初期ロード（編集時）や、選択肢マスタ（`MasterData`）の取得のみを担当。
   - フォームコンポーネントにPropsとしてデータを渡す。

2. **`_components/[機能名]-form.tsx` (Client Component)**
   - 見た目（JSX）の構築を担当。
   - ロジックはすべてカスタムフック（`useXxxForm`）に委譲する。
   - `Stack`, `SectionHeading` 等のUIコンポーネントを使用してレイアウトする。

3. **`_components/use-[機能名]-form.ts` (Custom Hook)**
   - **状態管理**: 全入力フィールドを `useState` で定義する。
   - **バリデーション**: `onBlur` イベントでのフィールド単位検証ロジックを実装。
   - **送信処理**: `handleSubmit` 内でZod一括チェックを行い、Server Actionを呼び出す。
   - **エラー管理**: `fieldErrors`, `generalError` ステートを持ち、UIにフィードバックする。

### B. 実装詳細ルール

1. **バリデーションロジック**
   - `lib/validations/` にZodスキーマを定義する。
   - フック内に `validateFieldOnBlur` ヘルパー関数を実装し、フォーカスが外れたタイミングで単一項目のエラーチェックを行うこと。
   - 送信時には `schema.safeParse(formData)` で全項目を検証すること。

2. **サーバー連携**
   - API Routes (`app/api/`) は作成しない。
   - `lib/actions/` に `createXxxAction`, `updateXxxAction` を定義し、`useTransition` (`startTransition`) 内で呼び出すこと。
   - サーバー側でも必ずZodスキーマによる再検証（`parseFormData`）を行うこと。

3. **コンポーネント分割**
   - フォームが長大になる場合（300行以上目安）は、セクション単位（例: `AddressFields`, `ProfileFields`）でサブコンポーネントに分割すること。
   - サブコンポーネントへのPropsバケツリレーを許容する。

## 4. 一覧画面・フィルター実装ガイドライン

`app/admin/(authenticated)/customers/page.tsx`（顧客一覧画面）の実装パターンを規範とする。

### A. アーキテクチャ（Client-Side Filtering）

サーバー負荷を軽減し、実装をシンプルに保つため、以下の構成を採用する。

1. **データ取得 (Server Component)**
   - `page.tsx` で、表示に必要なデータを**全件取得**する（ページネーションせず一括取得）。
   - 取得したデータをClient Componentに渡す。

2. **フィルタリング (Client Component)**
   - `_components/[機能名]-list.tsx` 内で `useState` により検索条件（キーワード、絞り込み項目）を管理する。
   - `useMemo` を使用して、メモリ上でデータのフィルタリングを実行する。
   - URLクエリパラメータによる管理は行わない（リロードで初期化される挙動とする）。

3. **ページネーション (Client Component)**
   - フィルタリング後の結果に対して、クライアントサイドでページネーション計算を行う。
   - `usePagination` フック（`hooks/use-pagination.ts`）を使用すること。

### B. 実装詳細ルール

1. **検索ロジック**
   - 検索フィルターロジックは `lib/helpers/[機能名]-filter.ts` 等に切り出し、テスト可能な状態にすること。

2. **CSVエクスポート**
   - クライアント側で表示中のデータをCSV化するのではなく、Server Action (`exportXxxAction`) を呼び出して生成すること。
   - サーバー側で再度同じフィルタリングロジックを適用してデータを生成する。
