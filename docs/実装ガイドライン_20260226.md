# 実装ガイドライン

本プロジェクト（マルコポーロ・ポータル）の実装規約をまとめたドキュメントです。
新しい画面や機能を作成する際は、本ガイドラインに従ってください。

---

## 1. 基本方針（技術スタック）

| カテゴリ | 技術 |
|---|---|
| フレームワーク | Next.js 16 (App Router, Turbopack) / React 19 / TypeScript 5 |
| UIライブラリ | shadcn/ui (Tailwind CSS 4) / アイコンは `lucide-react` |
| 通信 | Server Actions（API Routesは使用しない） |
| バリデーション | Zod 4（`lib/validations/` に定義） |
| 状態管理 | React Hook Form等は使用せず、標準の `useState`（Controlled Components）を採用 |
| DB / ORM | PostgreSQL 17 / Prisma 7（PrismaPg adapter） |
| 認証 | Auth.js v5 (next-auth@5.0.0-beta) JWT方式 |
| メール送信 | nodemailer（開発: MailPit / 本番: Resend SMTP） |
| テスト | Vitest 4 + jsdom |

## 3. コーディング規約

### A. 定数の一元管理

DBのコードやマスタ値をコード上で参照する場合は、文字列リテラルを直接書かず `lib/constants/` の定数を使用すること。

**悪い例:**
```ts
if (cc.community.code === "venture_auditor") { ... }
```

**良い例:**
```ts
import { COMMUNITY_CODE } from "@/lib/constants/community";
if (cc.community.code === COMMUNITY_CODE.VENTURE_AUDITOR) { ... }
```

**定数ファイルの配置規則:**

| 対象 | ファイル |
|---|---|
| コミュニティコード・名前・バッジ | `lib/constants/community.ts` |
| 顧客関連（会員区分、会員種別等） | `lib/constants/customer.ts` |
| イベント関連（ステータス等） | `lib/constants/event.ts` |
| 管理者関連（ロール等） | `lib/constants/admin.ts` |
| フォーム共通（NONE_VALUE等） | `lib/constants/form.ts` |

新しいドメイン固有の定数が必要な場合は、`lib/constants/[ドメイン名].ts` に追加すること。

### B. 定数管理の拡張パターン

**パターン1: Prisma Enum型 + Record + `as const`**

DBの enum 型を直接キーに使い、表示ラベルを型安全に管理する。

```ts
// lib/constants/customer.ts
import type { MemberCategory } from "@/lib/generated/prisma";

export const MEMBER_CATEGORY_LABELS: Record<MemberCategory, string> = {
  member: "会員",
  sponsor: "スポンサー",
  observer: "オブザーバー",
} as const;
```

**パターン2: Config型（label + variant + description）**

Badge表示などUIと密結合する場合は、表示設定をまとめたConfigオブジェクトを定義する。

```ts
// lib/constants/event.ts
import type { RsvpStatus } from "@/lib/generated/prisma";
import type { BadgeVariant } from "@/components/ui/badge";

export const RSVP_STATUS_CONFIG: Record<RsvpStatus, {
  label: string;
  variant: BadgeVariant;
  description: string;
}> = {
  attending: { label: "参加", variant: "default", description: "通常参加" },
  online: { label: "オンライン参加", variant: "online", description: "オンライン参加" },
  absent: { label: "不参加", variant: "destructive-outline", description: "不参加" },
  pending: { label: "未回答", variant: "secondary", description: "未回答" },
} as const;
```

**パターン3: 選択肢配列（readonly）**

Select/RadioGroupなどのUI選択肢には `readonly` 配列を使う。

```ts
export const AUDIT_MEMBER_TYPES: readonly { value: AuditMemberType; label: string }[] = [
  { value: "regular", label: "正会員" },
  { value: "online", label: "オンライン会員" },
] as const;
```

**パターン4: NONE_VALUE（Select未選択のsentinel値）**

Select系UIで「未選択」を表現する場合は `NONE_VALUE` を使う（空文字列ではなく明示的なsentinel値）。

```ts
// lib/constants/form.ts
export const NONE_VALUE = "__none__";
```

### C. 型安全性

- `any` は使用禁止。Zodから推論された型（`z.infer<typeof schema>`）またはPrismaの生成型を使用すること。
- 定数マップのキーにPrisma Enum型を使うことで、Enumの変更時にコンパイルエラーで検出できる。

### D. UIコンポーネント

- `components/ui/` 以下のshadcn UIコンポーネントを使用すること。
- アイコンは `lucide-react` を使用すること。

## 4. Server Actions

### A. ファイル配置・命名規則

| 規則 | 例 |
|---|---|
| 配置先 | `lib/actions/[ドメイン名].actions.ts` |
| ファイル先頭 | `"use server";` ディレクティブ必須 |
| 関数名 | `createXxxAction`, `updateXxxAction`, `deleteXxxAction` |
| 戻り値型 | `ActionResult` ベースのユニオン型 |

### B. ActionResult型

`lib/types/action.ts` に定義された基本型を使用する。

```ts
// lib/types/action.ts
export type ActionResult = {
  error?: string;
  fieldErrors?: Record<string, string[]>;
};
```

各Actionは用途に応じた結果型を定義する。

```ts
// redirect するアクション: 成功時は void を返す（redirectが例外をスロー）
export type UpdateEventResult =
  | ({ success: false } & ActionResult)
  | void;

// 値を返すアクション: success: true + データ
export type EventActionResult =
  | { success: true; eventId: number }
  | ({ success: false } & ActionResult);
```

### C. 標準構造（処理フロー）

すべてのServer Actionは以下の順序で処理を行う。

```ts
"use server";

import { revalidatePath } from "next/cache";
import { redirect } from "next/navigation";
import { requireAuthenticatedAdmin, canAccessEvent } from "@/lib/auth/permissions";
import { eventSchema } from "@/lib/validations/event";
import { formatZodFieldErrors } from "@/lib/validations/utils";
import * as eventRepo from "@/lib/repositories/event.repository";
import type { ActionResult } from "@/lib/types/action";

export async function updateEventAction(
  eventId: number,
  formData: unknown
): Promise<EventActionResult | void> {
  // 1. 認証
  const { admin, isSuper, scopedCommunityIds } = await requireAuthenticatedAdmin();

  // 2. 権限チェック（リソース固有のアクセス制御）
  const hasAccess = await canAccessEvent(admin, eventId);
  if (!hasAccess) {
    return { success: false, error: "このイベントへのアクセス権がありません" };
  }

  // 3. バリデーション（Zod safeParse）
  const parsed = eventSchema.safeParse(formData);
  if (!parsed.success) {
    return { success: false, fieldErrors: formatZodFieldErrors(parsed.error) };
  }

  // 4. DB操作（Repository経由）
  try {
    await eventRepo.updateEvent(eventId, { ... });
  } catch (err) {
    logServerError("updateEventAction", err);
    return { success: false, error: "イベントの更新に失敗しました" };
  }

  // 5. キャッシュ無効化 + リダイレクト
  revalidatePath("/admin/events");
  redirect("/admin/events");
}
```

**ポイント:**
- `formData` の型は `unknown` で受け取り、必ずZodで検証する
- Repository関数のエラーは `try/catch` でキャッチし、ユーザー向けメッセージを返す
- **`catch {`（無引数）は使わない。** 必ず `catch (err)` で受け取り、`logServerError("actionName", err)` でサーバー側ログを残す
- ユーザー向けメッセージとサーバーログは分離する（詳細な DB エラー内容を UI に出さない）
- Prisma の P2002（ユニーク制約違反）は `isPrismaUniqueViolationOnField(err, "email")` 等で **対象フィールドを判別** してからユーザー向けメッセージを返す
- リダイレクトする場合は `revalidatePath` → `redirect` の順で呼ぶ
- `formatZodFieldErrors()` でZodエラーをフィールド別のエラーマップに変換する

**エラーログ用ユーティリティ:**

| ファイル | 用途 |
|---|---|
| `lib/utils/log-error.ts` | `logServerError(context, err)` — Vercel Function Logs / 開発ターミナル向け |
| `lib/utils/prisma-error.ts` | `isPrismaUniqueViolationOnField(err, field)` — P2002 のフィールド判別 |

## 5. Repositoryパターン

### A. 配置・命名規則

| 規則 | 例 |
|---|---|
| 配置先 | `lib/repositories/[ドメイン名].repository.ts` |
| エクスポート形式 | 名前付き関数エクスポート（`export async function findAllEvents(...)`) |
| インポート | `import * as eventRepo from "@/lib/repositories/event.repository"` |

### B. 用途別の型定義

Repository内で、用途ごとにPrismaの返却型を拡張した型を定義する。

```ts
// lib/repositories/event.repository.ts
import type { Community, Customer, Event, Rsvp } from "@/lib/generated/prisma";

// 一覧用（リレーション + 集計）
export type EventForList = Event & {
  community: Community;
  _count: { rsvps: number };
};

// 詳細用（リレーション + ネスト）
export type EventForDetail = Event & {
  community: Community;
  rsvps: (Rsvp & {
    customer: Pick<Customer, "id" | "lastName" | "firstName" | "company">;
  })[];
};

// 案内メール用（必要最小限のフィールド）
export type EventForInvite = Event & {
  community: Community;
  rsvps: Pick<Rsvp, "customerId" | "status">[];
};
```

**ポイント:**
- Prisma生成型を `&` で拡張してリレーション型を付与する
- 不要なフィールドは `Pick` で絞る
- 型名は `XxxForYyy`（例: `EventForList`, `EventForDetail`）

### C. 論理削除パターン

物理削除は行わず、`deletedAt` カラムによる論理削除を使用する。

```ts
// 一覧取得: deletedAt: null で未削除のみ
export async function findAllEvents(...): Promise<EventForList[]> {
  return prisma.event.findMany({
    where: { deletedAt: null, ... },
  });
}

// 論理削除: deletedAt に現在時刻をセット
export async function softDeleteEvent(eventId: number): Promise<Event> {
  await prisma.event.findFirstOrThrow({
    where: { id: eventId, deletedAt: null },
  });
  return prisma.event.update({
    where: { id: eventId },
    data: { deletedAt: new Date() },
  });
}
```

## 6. データフロー（Server → Client）

### A. シリアライズ層

PrismaのDate型はServer Component → Client Component間で直接渡せないため、ISO文字列に変換するシリアライズ層を設ける。

```
Repository (Prisma型) → Serializer (Date→string) → Client Component (Serialized型)
```

### B. シリアライズ関数

`lib/serializers/[ドメイン名].ts` に配置する。

```ts
// lib/serializers/event.ts
import type { EventForList } from "@/lib/repositories/event.repository";
import type { SerializedEvent } from "@/lib/types/serialized";

export function serializeEventForList(e: EventForList): SerializedEvent {
  return {
    id: e.id,
    title: e.title,
    date: e.date.toISOString(),
    responseDeadline: e.responseDeadline?.toISOString() ?? null,
    community: {
      id: e.community.id,
      code: e.community.code,
      name: e.community.name,
    },
    // ...
  };
}
```

**変換ルール:**
- `Date` → `.toISOString()` で `string` に
- `Date | null` → `?.toISOString() ?? null` で `string | null` に
- リレーションは必要なフィールドのみ抽出してフラットに

### C. Serialized型

`lib/types/serialized.ts` に、シリアライズ後の型を一元管理する。

```ts
// lib/types/serialized.ts

// 共通マスタ型
export interface MasterData {
  id: number;
  name: string;
}

export interface CommunityOption {
  id: number;
  code: string;
  name: string;
}

// 用途別Serialized型
export interface SerializedEvent {
  id: number;
  title: string;
  date: string;           // Date → ISO文字列
  location: string | null;
  // ...
  community: CommunityOption;
}
```

**命名規則:** `Serialized` + ドメイン名 + 用途（例: `SerializedEventDetail`, `SerializedCustomerForInvite`）

### D. ページ構成パターン

```tsx
// page.tsx (Server Component)
import { getAuthenticatedAdmin } from "@/lib/auth/permissions";
import * as eventRepo from "@/lib/repositories/event.repository";
import { serializeEventForList } from "@/lib/serializers/event";
import { EventList } from "./_components/event-list";

export default async function EventsPage() {
  const { isSuper, scopedCommunityIds } = await getAuthenticatedAdmin();
  const events = await eventRepo.findAllEvents(scopedCommunityIds, isSuper);
  const serializedEvents = events.map(serializeEventForList);

  return <EventList events={serializedEvents} />;
}
```

## 7. フォーム実装ガイドライン

`app/admin/(authenticated)/customers/` の実装パターンを規範とする。

### A. ファイル構成と役割分担

1. **`page.tsx` (Server Component)**
   - データの初期ロード（編集時）や、選択肢マスタ（`MasterData`）の取得のみを担当。
   - フォームコンポーネントにPropsとしてデータを渡す。

2. **`_components/[機能名]-form.tsx` (Client Component)**
   - 見た目（JSX）の構築を担当。
   - ロジックはすべてカスタムフック（`useXxxForm`）に委譲する。

3. **`_components/use-[機能名]-form.ts` (Custom Hook)**
   - **状態管理**: 全入力フィールドを `useState` で定義する。
   - **バリデーション**: `onBlur` イベントでのフィールド単位検証ロジックを実装。
   - **送信処理**: `handleSubmit` 内でZod一括チェックを行い、Server Actionを呼び出す。
   - **エラー管理**: `useFieldErrors` フックを使用する。

### B. useFieldErrors フック

`lib/hooks/use-field-errors.ts` に定義された共通フック。フォームのエラー状態管理を統一する。

```ts
// lib/hooks/use-field-errors.ts
export function useFieldErrors() {
  const [fieldErrors, setFieldErrors] = useState<Record<string, string[]>>({});
  const [generalError, setGeneralError] = useState<string | null>(null);

  const clearFieldError = (field: string) => {
    setFieldErrors((prev) => {
      if (!prev[field]) return prev;
      const next = { ...prev };
      delete next[field];
      return next;
    });
  };

  return { fieldErrors, setFieldErrors, generalError, setGeneralError, clearFieldError };
}
```

**使い方:**
- `clearFieldError("title")` — `onBlur` / `onChange` 時に該当フィールドのエラーをクリア
- `setFieldErrors(result.fieldErrors)` — Server Action / Zod safeParseの結果をセット
- `setGeneralError(result.error)` — 汎用エラーメッセージをセット

### C. 実装詳細ルール

1. **バリデーションロジック**
   - `lib/validations/` にZodスキーマを定義する。
   - フック内に `validateFieldOnBlur` ヘルパー関数を実装し、フォーカスが外れたタイミングで単一項目のエラーチェックを行うこと。
   - 送信時には `schema.safeParse(formData)` で全項目を検証すること。

2. **サーバー連携**
   - API Routes (`app/api/`) は作成しない。
   - `lib/actions/` に `createXxxAction`, `updateXxxAction` を定義し、`useTransition` (`startTransition`) 内で呼び出すこと。
   - サーバー側でも必ずZodスキーマによる再検証を行うこと。

3. **コンポーネント分割**
   - フォームが長大になる場合（300行以上目安）は、セクション単位でサブコンポーネントに分割すること。
   - サブコンポーネントへのPropsバケツリレーを許容する。

### D. バリデーション拡張パターン

**パターン1: optional + literal（空文字列許容）**

任意入力フィールドで空文字列を許容する場合。

```ts
location: z
  .string()
  .max(255, "255文字以内で入力してください")
  .optional()
  .or(z.literal("")),
```

**パターン2: preprocess（入力値の正規化）**

Select等の入力値を前処理で正規化する場合。

```ts
const optionalId = z.preprocess(
  (v) => (v === null || v === undefined || v === "" || v === 0 ? null : Number(v)),
  z.number().int().positive().nullable().optional()
);
```

**パターン3: union + transform（複数形式の入力を統一）**

```ts
responseDeadline: z
  .union([z.coerce.date(), z.literal(""), z.null(), z.undefined()])
  .transform((val) => (val === "" || val === undefined ? null : val))
  .nullable()
  .optional(),
```

**パターン4: superRefine（相関チェック）**

複数フィールド間の整合性チェック。

```ts
const schema = z.object({
  date: z.coerce.date(),
  responseDeadline: z.coerce.date().nullable().optional(),
}).superRefine((data, ctx) => {
  if (data.responseDeadline && data.date && data.responseDeadline > data.date) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: "回答期限は開催日時より前に設定してください",
      path: ["responseDeadline"],
    });
  }
});
```

**パターン5: refineWithValidator（共通検証関数の再利用）**

カスタム検証関数を `superRefine` に統合するアダプタ。

```ts
// lib/validations/customer.ts
function refineWithValidator(validate: (v: string) => string | null) {
  return (v: string, ctx: z.RefinementCtx) => {
    const error = validate(v);
    if (error) ctx.addIssue({ code: z.ZodIssueCode.custom, message: error });
  };
}

// 使用例
phone: z.string().superRefine(refineWithValidator(validatePhone)).optional().or(z.literal("")),
```

## 8. 一覧画面・フィルター実装ガイドライン

### A. アーキテクチャ（Client-Side Filtering）

1. **データ取得 (Server Component)**
   - `page.tsx` で全件取得し、Client Componentに渡す。

2. **フィルタリング (Client Component)**
   - `_components/[機能名]-list.tsx` 内で `useState` により検索条件を管理する。
   - `useMemo` でメモリ上のフィルタリングを実行する。
   - URLクエリパラメータによる管理は行わない。

3. **ページネーション (Client Component)**
   - `usePagination` フック（`hooks/use-pagination.ts`）を使用する。

### B. フィルターロジック

検索フィルターロジックは `lib/helpers/[機能名]-filter.ts` に切り出し、テスト可能な状態にすること。

```ts
// lib/helpers/event-filter.ts
export interface EventListFilters {
  keyword: string;
  statuses: EventDisplayStatus[];
  eventTypeCodes: string[];
}

export interface FilterableEvent {
  id: number;
  title: string;
  date: string;
  location: string | null;
  // ...
}

export function filterAndSortEvents<T extends FilterableEvent>(
  events: T[],
  filters: EventListFilters
): EnrichedEvent<T>[] { ... }
```

**ポイント:**
- フィルタ条件のインターフェースと、フィルタ対象データの最小インターフェースを定義する
- ジェネリクス `<T extends FilterableXxx>` を使い、追加フィールドを保持する

### C. スペース区切りAND検索パターン

キーワード検索では、半角・全角スペースで分割したトークンによるAND検索を行う。

```ts
if (filters.keyword) {
  const tokens = filters.keyword
    .toLowerCase()
    .split(/[\s\u3000]+/)    // 半角・全角スペースで分割
    .filter(Boolean);         // 空トークン除去
  const searchTarget = `${event.title} ${event.location ?? ""} ...`.toLowerCase();
  const matches = tokens.every((token) => searchTarget.includes(token));
  if (!matches) return false;
}
```

### D. CSVエクスポート

- クライアント側で表示中のデータをCSV化するのではなく、Server Action (`exportXxxAction`) を呼び出して生成すること。
- サーバー側で再度同じフィルタリングロジックを適用してデータを生成する。

## 9. 認証・権限パターン

### A. 認証関数の使い分け

`lib/auth/permissions.ts` に定義された関数を場面に応じて使い分ける。

| 関数 | 用途 | 未認証時の挙動 |
|---|---|---|
| `getAuthenticatedAdmin()` | **Server Component**用 | `/admin/login` にリダイレクト |
| `requireAuthenticatedAdmin()` | **Server Action**用 | 例外をスロー |

**両関数は同じ `AuthenticatedAdmin` 型を返す。**

```ts
export interface AuthenticatedAdmin {
  admin: AdminForPermission;     // { id, role, adminCommunities }

  scopedCommunityIds: number[];  // アクセス可能なコミュニティIDリスト
}
```

### B. 使用例

```ts
// Server Component（page.tsx）
const { isSuper, scopedCommunityIds } = await getAuthenticatedAdmin();
const events = await eventRepo.findAllEvents(scopedCommunityIds, isSuper);

// Server Action
const { admin, isSuper, scopedCommunityIds } = await requireAuthenticatedAdmin();
const hasAccess = await canAccessEvent(admin, eventId);
```

### C. canAccess系関数

リソース固有のアクセス権を判定する関数群。

| 関数 | 判定対象 | ロジック |
|---|---|---|
| `canAccessCustomer(admin, customerId)` | 顧客 | super: 常にtrue / community_admin: 顧客がスコープ内コミュニティに所属 |
| `canAccessEvent(admin, eventId)` | イベント | super: 常にtrue / community_admin: イベントのコミュニティがスコープ内 |
| `canManageSurvey(admin, eventId)` | アンケート | スコープ + `community.hasSurvey` チェック（superでも必須） |

### C. バッチメール送信

大量のメール送信は `sendMailBatch()` で行う。

```ts
const BATCH_SIZE = 10;

export async function sendMailBatch(params: BatchMailParams): Promise<BatchMailResult> {
  for (let i = 0; i < customers.length; i += BATCH_SIZE) {
    const batch = customers.slice(i, i + BATCH_SIZE);
    const batchResults = await Promise.allSettled(
      batch.map((customer) => {
        // トークンからRSVP URL構築 → プレースホルダ置換 → 送信
        return sendMail({ ... });
      })
    );
    sendResults.push(...batchResults);
  }
  // 成功/失敗の集計
  return { sentCount, failedCount, failedNames, successCustomerIds };
}
```

**ポイント:**
- `BATCH_SIZE = 10` で分割し、バッチ単位で `Promise.allSettled` を使用
- `Promise.all` ではなく `Promise.allSettled` を使い、一部失敗でも他は処理継続
- 結果は `BatchMailResult` で成功数・失敗数・失敗顧客名を返す

### D. テンプレート・プレースホルダ
